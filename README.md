# Конструктор опросов

REST-сервис для создания опросов и сбора ответов (упрощённый аналог Google Forms).
Автор создаёт опрос с вопросами и вариантами ответа и публикует его. Пользователи
проходят опрос и отправляют ответы. После этого автор закрывает опрос и смотрит итоги.

Учебный проект по дисциплине РБПО, вариант 19.

**Стек:** Java 25, Spring Boot 4.1, Spring Security, JWT (JJWT 0.13, HS256), Spring Data JPA (Hibernate), PostgreSQL, Maven.

---

## Предметная модель

| Сущность | Таблица | Описание |
|---|---|---|
| Пользователь | `app.users` | учётная запись (логин, хэш пароля, роль, состояние) и профиль; автор опросов или респондент |
| Опрос | `app.surveys` | название, автор, сроки проведения, статус |
| Вопрос | `app.survey_questions` | текст, признак обязательности, принадлежит опросу |
| Вариант ответа | `app.question_options` | допустимые варианты ответа на вопрос (с сохранением порядка) |
| Участие | `app.survey_participations` | прохождение опроса конкретным пользователем |
| Ответ | `app.survey_answers` | выбранный вариант на вопрос в рамках участия |
| Сессия токенов | `app.user_sessions` | одна выданная пара access/refresh: сроки, устройство, статус refresh |

### Связи

```
users 1──* surveys              (автор опроса)
users 1──* survey_participations (респондент)
surveys 1──* survey_questions 1──* question_options
surveys 1──* survey_participations 1──* survey_answers
survey_questions 1──* survey_answers
```

### Жизненный цикл

```
Опрос:    DRAFT ──publish──► ACTIVE ──close──► CLOSED
Участие:  IN_PROGRESS ──submit──► SUBMITTED
          IN_PROGRESS ──(отказ респондента или закрытие опроса)──► ABANDONED
```

### Ограничения целостности (на уровне БД)

| Ограничение | Правило предметной области |
|---|---|
| `NOT NULL` + `CHECK (btrim(...) <> '')` | у пользователя, опроса, вопроса и варианта не может быть пустого имени или текста |
| `UNIQUE (username)` + `CHECK` по шаблону | логин уникален и состоит из латиницы, цифр, `_ . -` (3–50 символов) |
| `UNIQUE (email)` | один email принадлежит одному пользователю |
| `CHECK (role IN ('USER','ADMIN'))`, `CHECK (status IN ('ACTIVE','BLOCKED'))` | роли и состояния учётной записи только из допустимого набора |
| `CHECK (status IN (...))` | статусы только из допустимого набора |
| `surveys_dates_order` | опрос не может закончиться раньше, чем начался |
| `question_options_unique_value` | варианты ответа внутри вопроса не повторяются |
| `participations_one_per_user` | пользователь проходит опрос один раз |
| `participations_submitted_at` | время отправки есть тогда и только тогда, когда участие отправлено |
| `answers_one_per_question` | в рамках участия на вопрос дан один ответ |
| `user_sessions_refresh_token_unique` | каждый refresh-токен соответствует ровно одной сессии |
| `user_sessions.username → users.username` | сессия принадлежит существующему пользователю |
| `CHECK (status IN ('ACTIVE','USED','REVOKED'))` | статус сессии только из допустимого набора |
| `FOREIGN KEY ... ON DELETE CASCADE` | удаление объекта удаляет зависимые данные, и «висячих» ссылок не остаётся |

Правило «вопрос ответа принадлежит тому же опросу, что и участие» проверяется в сервисном слое.

## Бизнес-операции

| # | Операция | Запрос | Что делает | Когда отклоняется (409 Conflict) |
|---|---|---|---|---|
| 1 | Публикация опроса | `POST /api/surveys/{id}/publish` | DRAFT → ACTIVE; если дата начала не задана, ставит текущее время | опрос не в статусе DRAFT; в опросе нет вопросов; дата окончания уже прошла |
| 2 | Закрытие опроса | `POST /api/surveys/{id}/close` | ACTIVE → CLOSED; все незавершённые участия переводятся в ABANDONED; возвращает число брошенных участий | опрос не в статусе ACTIVE |
| 3 | Отправка участия | `POST /api/survey-participations/{id}/submit` | IN_PROGRESS → SUBMITTED; время отправки ставит сервер | участие уже отправлено или брошено; опрос не активен; срок опроса истёк; не отвечены обязательные вопросы (в ответе приходит их список) |
| 4 | Копирование опроса | `POST /api/surveys/{id}/copy` | создаёт новый черновик «Копия: …» с копиями всех вопросов и вариантов; автор копии — текущий пользователь | — (404, если опрос не найден) |
| 5 | Итоги опроса | `GET /api/surveys/{id}/results` | число отправленных участий и количество выборов каждого варианта по каждому вопросу (учитываются только отправленные участия) | опрос в статусе DRAFT |

### Связанные правила

- Новый опрос всегда создаётся как DRAFT. Статус опроса меняется **только** операциями `publish` и `close`. Попытка изменить его через PATCH отклоняется (400).
- Вопросы можно создавать, изменять и удалять только в черновике. Чтобы изменить уже опубликованный опрос, его копируют (операция 4).
- Участвовать можно только в активном опросе и только в пределах его сроков. Автор не может участвовать в собственном опросе.
- Отвечать и менять ответы можно только пока участие в статусе IN_PROGRESS. Значение ответа должно быть одним из вариантов вопроса.
- Участие отправляется только через `submit`. Через PATCH респондент может лишь отказаться от прохождения (`ABANDONED`).

### Корректность и целостность

- каждая операция выполняется в одной транзакции (`@Transactional`): она либо применяется целиком, либо откатывается;
- перед изменением проверяется текущее состояние связанных объектов;
- ограничения БД служат последним рубежом защиты (нарушение возвращается как 409);
- закрытие опроса и отправка участия блокируют строку опроса (`SELECT ... FOR UPDATE`), поэтому одновременные закрытие и отправка не могут привести к несогласованному состоянию.

## REST API (CRUD)

Для каждой сущности доступны операции:

| Метод | Путь | Ответ |
|---|---|---|
| `GET` | `/api/{resources}` | 200, массив |
| `GET` | `/api/{resources}/{id}` | 200 / 404 |
| `POST` | `/api/{resources}` | 201, созданный объект с `id` |
| `PATCH` | `/api/{resources}/{id}` | 200, обновлённый объект (меняются только переданные поля) |
| `DELETE` | `/api/{resources}/{id}` | 204 |

`{resources}`: `users`, `surveys`, `survey-questions`, `survey-participations`, `survey-answers`.

- автор опроса и респондент участия определяются по текущему пользователю; поля `authorId` при создании опроса и `respondentId` при создании участия игнорируются;
- `users` доступны только администратору (создание учётной записи с ролью, изменение имени, email, роли и состояния, удаление).

**Коды ошибок:**

| Код | Значение |
|---|---|
| `400` | некорректные входные данные (валидация, слабый пароль) |
| `401` | нет access-токена или он недействителен; неверный логин/пароль; учётная запись заблокирована; refresh недействителен, использован или отозван |
| `403` | пользователь определён, но прав недостаточно |
| `404` | объект не найден |
| `409` | операция недопустима в текущем состоянии данных или нарушает ограничение БД; повторная регистрация |

Тело ошибки: `{"error": "описание"}`. Тексты ошибок SQL, стектрейсы и хэши паролей клиенту не передаются.

## Аутентификация и авторизация

### Вход, регистрация и обновление токенов

Аутентификация выполняется по **JWT**. Логин и пароль передаются только при входе, дальше каждый запрос
к API несёт access-токен в заголовке `Authorization: Bearer <accessToken>`.

| Endpoint | Тело | Успех | Отказы |
|---|---|---|---|
| `POST /auth/login` | `{"username", "password", "deviceId"?}` | 200 + пара | 400 — пустое поле, 401 — неверные данные или учётная запись заблокирована |
| `POST /auth/register` | `{"username", "password", "name", "email"?, "deviceId"?}` | 201 + пара | 400 — некорректные данные, 409 — логин уже занят |
| `POST /auth/refresh` | `{"refreshToken"}` | 200 + новая пара | 400 — нет поля, 401 — refresh недействителен, просрочен, не того типа, использован или отозван |
| `GET /api/auth/me` | — (access в заголовке) | 200 — текущий пользователь | 401 |

Успешный ответ всех трёх `/auth/*`: `{"accessToken": "...", "refreshToken": "..."}`. Ошибочный ответ пары не содержит.
`/auth/refresh` не требует access-токена и пароля.

Регистрация:
- логин: 3–50 символов (латиница, цифры, `_ . -`), уникален;
- пароль: не короче 8 символов и не длиннее 72 байт (ограничение BCrypt), содержит заглавную и строчную буквы и цифру, не совпадает с логином;
- зарегистрированный пользователь всегда получает роль `USER`; поле `role` в запросе игнорируется;
- создание пользователя и сохранение его первой сессии выполняются в одной транзакции: если сессия не сохранилась, пользователь не создаётся.

Пароли хранятся только в виде хэша **BCrypt** (стоимость 12). Вход проверяет `AuthenticationManager`
(`DatabaseUserDetailsService` + `PasswordEncoder`); ответ на неудачный вход одинаков для неверного пароля,
несуществующего логина и заблокированной учётной записи.

### Access- и refresh-токены

Оба токена — JWT, подписанные **HS256** ключом из переменной окружения `JWT_SECRET` (не менее 32 случайных байтов).

| | Access | Refresh |
|---|---|---|
| Назначение | доступ к API | получение новой пары |
| Срок жизни (`application.yml`) | `jwt.access-ttl`, по умолчанию 15 минут | `jwt.refresh-ttl`, по умолчанию 7 дней |
| Передача | заголовок `Authorization: Bearer` | JSON-тело `POST /auth/refresh` |
| Claim `type` | `access` | `refresh` |

Claims каждого токена: `jti` (новый UUID при каждой выдаче), `iss` (`rbpolab1`), `sub` (логин), `type`, `iat`, `exp`.
Проверка: подпись, алгоритм, срок действия, издатель, наличие обязательных claims и значение `type`.
JWT-фильтр принимает только access, обработчик обновления — только refresh.

JWT подписан, но не зашифрован: содержимое токена читается без ключа, поэтому в нём нет пароля, хэша и других секретов.
Роль пользователя в токен не записывается: фильтр при каждом запросе загружает пользователя из БД,
поэтому блокировка или смена роли действует сразу, без ожидания истечения access.

### Refresh-сессии и ротация

Каждая выданная пара записывается в `app.user_sessions` (одна запись — одна пара):
токены, их сроки (совпадают с `exp` с точностью до секунды), логин, `deviceId`, статус.

| Статус | Значение |
|---|---|
| `ACTIVE` | refresh ещё не использован и не отозван |
| `USED` | refresh обменян на новую пару |
| `REVOKED` | refresh отозван |

Обновление пары (`POST /auth/refresh`) выполняется в одной транзакции:
1. refresh проверяется как JWT (подпись, срок, `type = refresh`);
2. сессия находится по refresh-токену и **блокируется** (`SELECT ... FOR UPDATE`);
3. проверяются: владелец (`sub`), статус `ACTIVE`, срок `refreshTokenExpiry > now`, существование и состояние `ACTIVE` пользователя;
4. прежняя сессия переводится в `USED`, для новой пары создаётся новая запись `ACTIVE` с тем же пользователем и `deviceId`.

Корректность:
- **одновременные запросы** с одним refresh: блокировка строки выстраивает их в очередь, успешен только первый;
- **повторное предъявление** уже использованного (`USED`) refresh означает вероятную кражу токена: сессия переводится в `REVOKED`,
  возвращается 401 без новой пары. Изменение `REVOKED` фиксируется, несмотря на отказ
  (`@Transactional(noRollbackFor = InvalidTokenException.class)`); все проверки выполняются до изменения данных;
- **техническая ошибка** сохранения новой пары откатывает всю операцию: прежняя сессия не остаётся в `USED`;
- отзыв всей цепочки обновлений и немедленный отзыв уже выданного access не реализуются (не требуются).

### Состояние учётной записи

| Состояние | Вход | Обновление пары | Выданный ранее access |
|---|---|---|---|
| `ACTIVE` | разрешён | разрешено | принимается |
| `BLOCKED` | запрещён (401) | запрещено (401) | не принимается (401) |

Блокирует и разблокирует пользователей администратор (`PATCH /api/users/{id}` с `{"status": "BLOCKED"}`).
Администратор не может изменить собственную роль или состояние и не может удалить сам себя.

### Почему CSRF-защита отключена

CSRF-атака заставляет браузер отправить запрос, к которому он **сам** прикладывает реквизиты (cookie).
В этом приложении реквизиты — access-токен в заголовке и refresh в теле запроса — клиент передаёт явно,
браузер их автоматически не добавляет, а сторонняя страница их не знает. Сессии и cookie для аутентификации
не используются (`SessionCreationPolicy.STATELESS`), поэтому CSRF-токены не нужны.
Если токены будут перенесены в cookie, CSRF-защиту необходимо вернуть.

### Роли и права

- **USER** — создаёт и ведёт свои опросы, проходит чужие опросы;
- **ADMIN** — модератор: управляет пользователями, имеет доступ ко всем опросам, участиям и ответам.

| Действие | USER | ADMIN |
|---|---|---|
| Просмотр опросов и вопросов | все | все |
| Создание и копирование опроса | автор — он сам | автор — он сам |
| Изменение, удаление, публикация, закрытие опроса; итоги | только своего | любого |
| Смена автора опроса | нет | да |
| Создание, изменение, удаление вопросов | только в своём опросе | в любом |
| Начать участие | да (не в своём опросе) | да (не в своём опросе) |
| Ответы, отправка, отказ от участия | только в своём участии | нет |
| Просмотр участий и ответов | свои и в своих опросах | все |
| Удаление участия | своего | любого |
| Управление пользователями | нет | да |

Правила задаются в два уровня:
- `SecurityFilterChain` — по URL: без токена доступны только `POST /auth/login`, `/auth/register`, `/auth/refresh`; `/api/users/**` — только ADMIN; остальной `/api/**` — только с действующим access; всё прочее запрещено (`denyAll`);
- `@PreAuthorize` — на методах контроллеров: роль (`hasRole('ADMIN')`) и владение объектом (`@access.canManageSurvey(#id)` и т. п.).

Если объект не существует, возвращается 404; если существует, но недоступен пользователю — 403.

## Безопасность доступа к БД

- приложение подключается к БД пользователем `survey_service`, которому разрешены только `SELECT, INSERT, UPDATE, DELETE` в схеме `app`. Создавать, изменять и удалять таблицы он не может;
- структурой БД владеет отдельный пользователь `survey_owner`;
- логин и пароль БД и ключ подписи JWT не хранятся в репозитории, а передаются через переменные окружения `DB_USER`, `DB_PASSWORD`, `JWT_SECRET`;
- сервису разрешено только читать, добавлять и изменять записи `app.user_sessions` (без `DELETE`): история выдачи токенов сохраняется;
- все запросы к БД параметризованы (Spring Data JPA / JPQL с параметрами), строки SQL из пользовательского ввода не склеиваются.

## Запуск

### 1. Подготовка PostgreSQL (один раз, от имени суперпользователя `postgres`)

```sql
CREATE ROLE survey_owner   LOGIN PASSWORD '<пароль владельца>';
CREATE ROLE survey_service LOGIN PASSWORD '<пароль сервиса>';
```
```sql
CREATE DATABASE surveys OWNER survey_owner;
```
Подключившись к базе `surveys`:
```sql
REVOKE ALL ON DATABASE surveys FROM PUBLIC;
GRANT CONNECT ON DATABASE surveys TO survey_owner, survey_service;
CREATE SCHEMA app AUTHORIZATION survey_owner;
GRANT USAGE ON SCHEMA app TO survey_service;
ALTER DEFAULT PRIVILEGES FOR ROLE survey_owner IN SCHEMA app
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO survey_service;
ALTER DEFAULT PRIVILEGES FOR ROLE survey_owner IN SCHEMA app
    GRANT USAGE, SELECT ON SEQUENCES TO survey_service;
```

### 2. Таблицы и тестовые данные

В базе `surveys` выполнить по порядку:
1. `db/schema.sql` — таблицы, ограничения, права;
2. `db/data.sql` — тестовые данные.

Повторный запуск этих двух скриптов сбрасывает БД в исходное состояние.

**Тестовые данные:** пользователи Иван (1), Мария (2), Олег (3); активный опрос
«Качество столовой» (1) с двумя вопросами, по которому Мария уже отправила ответы, а Олег
ответил не на все вопросы; черновик «Учебные курсы» (2) с вопросом; пустой черновик (3).

### 3. Запуск приложения

Сгенерировать ключ подписи JWT (32 случайных байта в Base64), например в PowerShell:
```powershell
$bytes = New-Object byte[] 32
[System.Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($bytes)
[Convert]::ToBase64String($bytes)
```
или в Linux: `head -c 32 /dev/urandom | base64`.

Задать переменные окружения и запустить:
```
DB_USER=survey_service
DB_PASSWORD=<пароль сервиса>
JWT_SECRET=<ключ в Base64>
```
```
./mvnw spring-boot:run
```
Приложение доступно на `http://localhost:8080`. Без `JWT_SECRET` или с ключом короче 32 байт приложение не запускается.

| 2. CRUD по всем сущностям | все CRUD-операции от имени отдельного пользователя и администратора |
| 3. Права доступа | попытки изменить чужие данные, подменить автора или респондента, отказы 403 и 409 |
| 4. Бизнес-сценарий | пять бизнес-операций от имени разных пользователей, включая отказы |

Каждый запрос проверяет ожидаемый HTTP-код (вкладка Tests). Перед прогоном сбросить БД (шаг 2 запуска)
и запустить приложение. Папки выполняются по порядку: 2–4 используют токены из папки 0.

Проверка сессий в БД во время сценария папки 1:
```sql
SELECT username, device_id, status, created_at FROM app.user_sessions ORDER BY created_at;
```
После обновления пары первая запись Марии — `USED`, вторая — `ACTIVE`; после повторного предъявления
старого refresh первая — `REVOKED`, вторая — `ACTIVE`, новых записей не появляется.

## Структура проекта

```
src/main/java/ru/muravyev/rbpolab1
├── controller   — обработка HTTP-запросов, преобразование сущностей в DTO
├── dto          — объекты запросов и ответов API
├── entity       — JPA-сущности
├── exception    — исключения и их преобразование в HTTP-ответы
├── repository   — доступ к БД (Spring Data JPA)
├── security     — Spring Security, JWT (создание и проверка токенов, фильтр), загрузка учётных записей, проверки владения
└── service      — бизнес-логика, проверки, транзакции
src/test/java/.../security/JwtTokenProviderTest — модульные тесты создания и проверки JWT
db/              — SQL-скрипты схемы и тестовых данных
postman/         — коллекция запросов
```

Модульные тесты JWT (`JwtTokenProviderTest`) запускаются без БД: `./mvnw test` или из IDE.
